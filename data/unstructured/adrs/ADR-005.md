# ADR-005: Idempotency Keys & Exactly-Once Financial Commit Semantics

- **Status:** `ACCEPTED`
- **Owner:** `team-payments` (`#payments-eng`)
- **Decision Date:** `2024-10-03`
- **Governed APIs:** `api-payments-charge-v2` (`CONSTRAINS`), `api-payments-refund-v2` (`MANDATES`), `api-checkout-submit-v1` (`MANDATES`), `api-billing-invoice-v1` (`MANDATES`), `api-orders-create-v2` (`MANDATES`), `api-ledger-post-v2` (`MANDATES`)

## Context

Mobile network retries, load-balancer timeouts, and checkout saga replays previously caused duplicate customer card charges and imbalanced invoices whenever callers retried `POST` requests after an ambiguous HTTP `504` response.

## Decision

1. **Mandatory `Idempotency-Key` Header:** Every mutating financial endpoint — including `api-payments-charge-v2`, `api-payments-refund-v2`, `api-checkout-submit-v1`, `api-billing-invoice-v1`, `api-orders-create-v2`, and `api-ledger-post-v2` — MUST require a caller-generated UUIDv4 `Idempotency-Key` HTTP header.
2. **Atomic Deduplication Ledger:** `svc-payments` and `svc-ledger` store `(caller_service_id, idempotency_key, request_sha256, response_payload)` inside the same Cloud Spanner read-write transaction in `asia-southeast3` that commits the payment state and double-entry ledger journal (`REQ-005`).
3. **72-Hour Replay & Conflict Semantics:** Replaying the same `Idempotency-Key` with an identical payload hash within 72 hours returns the cached original HTTP status and body. Reusing a key with a mismatched payload returns HTTP `409 Conflict`.

## Consequences

- **Zero Double Charges:** Safe client retries from `svc-checkout`, `svc-billing`, and `svc-partner-gw` eliminate duplicate authorizations during transient network blips.
- **Contract Immutability:** Any schema change to `api-payments-charge-v2` request canonicalization MUST preserve `request_sha256` compatibility across in-flight 72-hour retry windows.
